## 〇、规范制定方法

本规范非凭空制定，而是对 `src/components/ui/Icons.vue` 中现有 39 个图标的 SVG 写法进行逆向提取，归纳已有规律后上升为标准。所有规则均标注**事实依据**（现有图标中的对应案例），确保新图标与现有图标风格一致。

**现有图标统计基础**：

| 统计维度 | 数据 |
|---------|------|
| 图标总数 | 39 |
| viewBox | 全部 24×24 |
| 主体 stroke-width | 1.75（35 个）/ 2.0（3 个 UI 图标）/ fill-only（1 个 i-ui-more） |
| stroke-linecap / linejoin | 100% round |
| fill 模式 | fill="none"（38 个）/ fill="currentColor"（1 个 i-ui-more） |
| 路径元素数量 | 1-6 个，中位数 3，均值 2.77 |
| 使用 fill 点睛的图标 | 5 个（i-relic-omega, i-bld-nano-forge, i-bld-dark-capture, i-bld-dark-well, i-bld-holo-core） |

## 一、画布规则

### 1.1 画布尺寸

- **统一 viewBox**：`0 0 24 24`，不可使用其他尺寸。
- **事实依据**：39/39 个现有图标全部使用 `viewBox="0 0 24 24"`，无例外。

### 1.2 安全边距

- **关键内容控制在 2-20 范围**（即四周各留 2px 安全边距）。
- **坐标允许触及 0 和 24**，但仅限以下两种情况：
  1. 装饰性外环/轨道（如 i-res-dark 的 `r=11` 触及 1-23，i-tech-dyson 的椭圆 `rx=10`）
  2. 需要满幅视觉张力的主体轮廓（如 i-res-energy 闪电从 y=2 到 y=22）
- **禁止**：核心可辨识结构（图标主体形状的关键顶点、转角）超出 2-20 范围。

### 1.3 对齐与网格

- **中心对齐**：所有图标以 (12, 12) 为视觉中心绘制。
- **坐标取整**：路径坐标优先使用整数（如 `M3 12` 而非 `M3.2 12.1`），仅在曲线控制点允许小数（如 `.5`、`.6`）。
- **45° 对角线例外**：45° 对角线线段端点允许使用 `.5` 小数坐标（如 `M14.5 17.5`），因为整数无法精确表达 45° 线段在两轴上的等长投影。但若可通过调整起点使所有端点取整且保持 45° 斜率（如 `M14 17 l11 11`），则应优先取整。
- **事实依据**：现有图标中 i-nav-tech（`cx="5" cy="5"`）、i-res-dark（`cx="12" cy="12"`）等均严格中心对齐；i-bld-reactor 的辐射线端点 `5.6`、`2.1` 是曲线控制点小数坐标的合理用例；i-ui-sword 的 `14.5`、`17.5` 是 45° 对角线端点小数坐标的用例（v2.0 微调时已取整为 `14`、`17`）。

### 1.4 symbol 模板

每个新图标必须使用以下模板（属性顺序保持一致）：

```html
<symbol id="i-{category}-{name}" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="1.75" stroke-linecap="round" stroke-linejoin="round">
  <!-- 路径元素 -->
</symbol>
```

- **事实依据**：35/39 个现有图标使用完全相同的属性组合。2 个 UI 图标（i-ui-check/i-ui-arrow-right）使用 `stroke-width="2"`，1 个（i-ui-more）使用 `fill="currentColor"` 无 stroke——这些是 UI 工具图标的特殊变体，新游戏图标不适用。（i-close 已删除，不再计入）

## 二、路径预算

### 2.1 路径元素数量标准

| 复杂度等级 | 元素数量 | 适用场景 | 现有案例 |
|-----------|---------|---------|---------|
| 极简 | 1 个 | 单一强隐喻图标 | i-res-energy（1 path 闪电）、i-unit-guard（1 path 盾牌） |
| 标准 | 2-3 个 | 大多数图标 | i-nav-home（3）、i-nav-army（2）、i-bld-reactor（2）、i-bld-lab（2） |
| 丰富 | 4-5 个 | 复合概念、矩阵高稀有度 | i-bld-quantum（4）、i-bld-deep-drill（4）、i-bld-neural-hub（5） |
| 上限 | 6 个 | 仅限多节点网络结构 | i-nav-tech（6） |

> **元素计数规则**：`<path>`、`<circle>`、`<rect>`、`<ellipse>` 各计 1 个元素。单个 `<path>` 内含多个 `M` 子路径仍计 1 个元素。

### 2.2 超标处理

- **硬性上限**：不超过 6 个元素。超过 6 个需设计说明书面理由，经评审通过方可接入。
- **复杂概念处理原则**：用抽象隐喻而非堆细节。例如：
  - "量子计算核心"不要画芯片+量子比特+轨道+节点（8+ 元素），而用"同心圆+交叉轨道"抽象表达（3-4 元素，参考 i-bld-quantum）。
  - "星际熔炉"不要画火焰+炉体+管道+材料（7+ 元素），而用"核心圆+辐射线+虚线环"表达（3 元素，参考 i-bld-stellar-forge）。

### 2.3 路径合并建议

- 多条独立直线段应合并为单个 `<path>` 的子路径（用 `M` 分隔），减少元素计数。
- **事实依据**：i-nav-tech 的 4 条连接线合并为 1 个 `<path d="M7 7l3 3M17 7l-3 3M7 17l3-3M17 17l-3-3"/>`；i-bld-reactor 的 8 条辐射线合并为 1 个 `<path d="M12 3v3M12 18v3M3 12h3..."/>`。

## 三、线宽体系

### 3.1 线宽分级

| 线宽 | 用途 | 适用元素 | 现有案例 |
|------|------|---------|---------|
| **1.75** | 主体线宽（默认） | 所有游戏内容图标的主体轮廓 | 35/39 个图标 |
| **2.0** | UI 工具图标加粗 | 仅限 check/arrow 等高频交互图标 | i-ui-check, i-ui-arrow-right |
| **1.5** | 辅助/装饰线 | 虚线轨道、能量场、传感器波纹等辅助元素 | *现有图标中未显式使用，本规范新增* |

### 3.2 线宽使用规则

- **新游戏图标默认 `stroke-width="1.75"`**，写在 `<symbol>` 属性上。
- **辅助装饰线允许 `stroke-width="1.5"`**，写在具体元素上覆盖 symbol 默认值。适用场景：
  - stroke-dasharray 虚线轨道（现有 i-res-dark 等用 dasharray 表达轨道，新图标可同时降低线宽增强层次）
  - 能量场/传感器波纹等非主体装饰
- **禁止**：主体轮廓使用 1.5 或 2.0 线宽；一个图标内出现 3 种以上线宽。

### 3.3 线宽一致性

- 同一图标内，同级视觉层次的线条必须使用相同线宽。
- 不同线宽用于区分主次关系（主体 1.75 > 辅助 1.5），不可随意混用。

## 四、线条风格

### 4.1 端点与连接

- **stroke-linecap**：`round`（无例外）
- **stroke-linejoin**：`round`（无例外）
- **事实依据**：39/39 个现有图标全部使用 round，是图标风格统一的基础。

### 4.2 填充规则

- **默认**：`fill="none"`（写在 symbol 属性上）
- **点睛填充例外**：仅以下场景允许 `fill="currentColor"`：

| 点睛类型 | 尺寸 | 透明度 | 现有案例 |
|---------|------|--------|---------|
| 微点（圆心/节点） | r ≤ 1 | 不透明 | i-relic-omega (`r=".5"`)、i-bld-nano-forge (`r="1"`)、i-bld-dark-capture (`r="1"`) |
| 小点（核心） | r = 2 | 不透明 | i-bld-dark-well (`r="2"`) |
| 半透明区域 | r ≤ 3 | `opacity="0.3"` | i-bld-holo-core (`r="3" opacity="0.3"`) |
| 全填充图标 | — | 不透明 | i-ui-more（3 个实心圆点，UI 工具图标唯一例外） |

- **禁止**：大面积实心填充（r > 3 且不透明）；多个元素同时使用 fill 点睛（每个图标最多 1 个 fill 点睛元素）。

### 4.3 虚线（stroke-dasharray）

- **用途**：表达轨道、能量场、传感器波纹、引力线等非物质/不稳定结构。
- **现有 dasharray 模式**：

| 模式 | 视觉效果 | 现有案例 |
|------|---------|---------|
| `"1 2"` | 短虚线点 | i-bld-silicon-ring、i-bld-dark-detector |
| `"1 3"` | 稀疏点线 | i-res-dark（外环） |
| `"2 2"` | 均匀虚线 | i-res-dark（中环）、i-bld-dark-capture、i-bld-dark-well |
| `"2 3"` | 中等虚线 | i-bld-stellar-forge |
| `"1 2.5"` | 细密点线 | i-tech-dark-scan、i-tech-singularity |

- **使用建议**：同一图标内最多 2 种 dasharray 模式（参考 i-res-dark 同时使用 `"2 2"` 和 `"1 3"` 区分两层轨道）。

### 5.2 组合语义规则

- **主形状决定一级语义**：图标的主体轮廓形状决定其所属语义类别。
- **辅助形状传递子类语义**：在主形状上叠加辅助元素细化含义。例如：
  - 盾形 + 勾 → 已完成的防御（i-nav-army）
  - 盾形 + 传感器线 → 探测型防御（i-bld-dark-detector）
  - 六边形 + 内菱形 → 晶体培育结构（i-bld-crystal-nursery）
- **跨语义组合**：允许两个形状组合表达复合概念（如 i-nav-relic = 菱形 + 层叠线 = 晶体 + 历史层次），但不宜超过 2 种基础形状。

### 5.3 扇区视觉语言

同一扇区的图标应共享视觉语言基调：

| 扇区 | 视觉语言基调 | 主形状偏好 | 现有参照图标 |

## 六、扇区色系映射

### 6.1 图标单色原则

- **图标本身不包含颜色信息**：所有图标通过 `stroke="currentColor"` 和 `fill="currentColor"` 继承父元素的文字颜色。
- **颜色由使用场景注入**：CSS 通过 `color` 属性为图标着色，图标 SVG 内不写 `stroke="#xxx"` 或 `fill="#xxx"`。
- **事实依据**：39/39 个现有图标全部使用 `stroke="currentColor"`，5 个 fill 点睛元素全部使用 `fill="currentColor"`。

### 6.2 扇区色系对照表

以下色值来自 `src/data/buildings.ts` 的 `SECTORS` 定义和 `src/data/tech.ts` 的 `TECH_BRANCHES` 定义：

| 扇区 | 色值 | 色名 | 数据来源 |
|------|------|------|---------|
| 能量扇区 | `#00E5FF` | 能量青 | SECTORS.energy / TECH_BRANCHES.energy |
| 晶体扇区 | `#34D399` | 晶体绿 | SECTORS.crystal / TECH_BRANCHES.crystallography |
| 合金扇区 | `#FFB627` | 合金橙 | SECTORS.alloy / TECH_BRANCHES.materials |
| 数据扇区 | `#A78BFA` | 数据紫 | SECTORS.data / TECH_BRANCHES.computing |
| 暗物质扇区 | `#E84393` | 暗物质粉 | SECTORS.dark |

### 6.3 稀有度色系对照表

以下色值来自 `src/data/relics.ts` 的 `RARITY_INFO` 定义：

| 稀有度 | 色值 | 色名 |
|--------|------|------|
| 普通 | `#8B96A8` | 灰蓝 |
| 稀有 | `#00E5FF` | 能量青 |
| 史诗 | `#A78BFA` | 量子紫 |
| 传说 | `#FFB627` | 传奇金 |

### 6.4 色彩注入方式

- **扇区色注入**：建筑/科技图标通过父容器的 `color` CSS 属性继承扇区色。
- **稀有度色注入**：遗物图标通过遗物卡片的 `--c` CSS 变量注入稀有度色（参考 RelicView.vue 的 `:style="{ '--c': getRarityColor(r.rarity) }"`）。
- **图标内部禁止硬编码颜色**：确保同一图标可在不同扇区/稀有度下复用。

## 七、命名规范

### 7.1 新图标命名格式

```
i-{category}-{name}
```

| 字段 | 说明 | 示例 |
|------|------|------|
| `i-` | 图标固定前缀 | — |
| `{category}` | 实体类别 | nav / res / ui / relic / tech / bld / branch / stronghold / unit |
| `{name}` | 语义名，kebab-case | energy-frag / mil-basic / raider |

### 7.2 类别前缀对照表

| 类别前缀 | 对应实体 | 示例 |
|---------|---------|------|
| `i-nav-` | 导航项 | `i-nav-home`、`i-nav-build`、`i-nav-relic` |
| `i-res-` | 资源 | `i-res-energy`、`i-res-crystal`、`i-res-dark` |
| `i-ui-` | 界面工具图标 | `i-ui-check`、`i-ui-arrow-right`、`i-ui-sword` |
| `i-relic-` | 遗物 | `i-relic-energy-1`、`i-relic-crystal-2`、`i-relic-silence` |
| `i-tech-` | 科技 | `i-tech-mil-basic`、`i-tech-weapon`、`i-tech-explore-1` |
| `i-bld-` | 建筑 | `i-bld-extractor`、`i-bld-dyson`、`i-bld-refinery` |
| `i-branch-` | 科技分支 | `i-branch-military`、`i-branch-explore`、`i-branch-crystal` |
| `i-stronghold-` | 据点类型 | `i-stronghold-raider`、`i-stronghold-beast` |
| `i-unit-` | 兵种 | `i-unit-psionic`、`i-unit-assault` |

### 7.3 旧图标统一化命名

- **v2.0 取消旧图标命名豁免**：v1.1 中"现有 39 个旧图标 id 不做重命名"的条款已废止。
- 所有旧图标须统一到 `i-{category}-{name}` 格式，重命名已于 v0.37 全部落地（过程梳理文档已退役，git 历史可查）；当前格式以本规范为准。
- 新增 3 个类别前缀以覆盖旧图标所属类别：`nav`（导航）、`res`（资源）、`ui`（界面工具）。
- **例外保留**：旧扇区扩展建筑图标（如 `i-bld-crystal-nursery`、`i-bld-nano-forge`）统一加上 `i-bld-` 前缀（如 `i-bld-crystal-nursery`、`i-bld-nano-forge`），同时保持原语义名不变。
- 重命名后旧 id 不再保留，引用方须同步修改（分期执行方案见统一化梳理记录 §5.3）。

### 7.4 命名禁忌

- **禁止使用中文**：symbol id 仅限小写字母、数字、连字符。
- **禁止使用下划线**：用连字符 `-` 分隔，不用下划线 `_`（与 SVG id 命名惯例一致）。
- **禁止缩写歧义**：`mil` 可接受（military 缩写常见），但避免单字母缩写如 `i-tech-m-1`。
- **数字编号**：同系列递进用数字尾缀（`-1`、`-2`、`-3`），放在最后（如 `i-relic-energy-1`）。

## 八、可读性测试标准

### 8.1 测试尺寸

每个新图标必须在以下三个尺寸下通过可读性测试：

| 测试尺寸 | 使用场景 | 判定标准 |
|---------|---------|---------|
| **24px** | 标准图标展示（卡片、列表） | 所有线条清晰可辨，无粘连 |
| **20px** | 紧凑展示（科技树节点、导航栏） | 主体形状可辨识，辅助细节允许模糊 |
| **16px** | 最小展示（资源栏角标、小标签） | 主体轮廓可辨识，能与相邻图标区分 |

### 8.2 测试方法

#### 方法 A：HTML 测试页（推荐）

在项目内创建临时测试页面 `src/dev/IconTest.vue`（不提交到生产）：

```html
<template>
  <div class="test-grid">
    <div v-for="id in testIds" :key="id" class="test-cell">
      <span class="label">{{ id }}</span>
      <svg class="icon" width="24" height="24"><use :href="`#${id}`" /></svg>
      <svg class="icon" width="20" height="20"><use :href="`#${id}`" /></svg>
      <svg class="icon" width="16" height="16"><use :href="`#${id}`" /></svg>
    </div>
  </div>
</template>
```

- 每个 icon 在 24/20/16 三尺寸下并排展示。
- 在浏览器中目视检查每个尺寸的可辨识度。
- 测试完成后删除该文件或保留在 dev 目录不参与构建。

#### 方法 B：浏览器缩放截图

- 在游戏页面中通过 DevTools 将图标容器缩放至目标尺寸。
- 截图后在 100% 缩放比下检查可辨识度。

#### 方法 C：批量截图脚本（可选）

- 使用 Playwright 截取测试页面的三尺寸截图，保存到 `docs/test-screenshots/` 目录便于对比。

### 8.3 可读性判定细则

| 判定项 | 通过标准 | 不通过示例 |
|--------|---------|-----------|
| 主体可辨识 | 16px 下能认出主体形状类型（圆/盾/菱形等） | 16px 下所有线条糊成一团 |
| 线条不粘连 | 24px 下相邻线条间距 ≥ 1px（即 viewBox 中 ≥ 1 单位） | 两条 1.75 线宽线条间距 < 1 单位 |
| 点睛不丢失 | 16px 下 fill 点睛仍可见（r ≥ 0.5 在 16px 下约 0.33px，需酌情放大） | r=".3" 的点睛在 16px 下完全不可见 |
| 与相邻图标可区分 | 同尺寸下与同类别其他图标并排时不会混淆 | 两个菱形图标在 16px 下看起来一样 |

### 8.4 不过审处理

- 未通过可读性测试的图标**不可接入 Icons.vue**。
- 需调整路径：简化细节、增大间距、放大点睛元素，重新测试通过后方可接入。

## 九、遗物矩阵规则

### 9.1 矩阵结构

遗物图标按 **5 资源类型 × 4 稀有度** 矩阵设计。资源类型通过基础形状区分，稀有度通过路径复杂度递增体现。

#### 5 资源类型的基础形状

| 资源类型 | 基础形状 | 视觉锚点 | 现有参照 |
|---------|---------|---------|---------|
| 能量 | 闪电 / 同心圆 | 动态、辐射 | i-res-energy, i-res-dark |
| 晶体 | 菱形 | 锐利、折射 | i-tech-deep-mine, i-nav-relic |
| 合金 | 六边形 | 结构、稳固 | i-res-alloy |
| 数据 | 矩形 + 节点 | 网格、信息 | i-res-data, i-nav-tech |
| 暗物质 | 圆 + 虚线 | 漩涡、虚实 | i-bld-dark-detector, i-bld-dark-well |

#### 4 稀有度的复杂度递增

| 稀有度 | 元素数量 | 视觉特征 | 设计方向 |
|--------|---------|---------|---------|
| 普通 | 2 个 | 单一主体形状，无装饰 | 碎片、碎屑、微粒 |
| 稀有 | 3 个 | 主体 + 1 层细节 | 结晶体、凝聚体、棱镜 |
| 史诗 | 4 个 | 主体 + 2 层细节或轨道 | 碎片+轨道、核心+辐射 |
| 传说 | 5 个 | 主体 + 多层结构 + 点睛 | 奇点、之眼、协议 |

### 9.2 遗物矩阵表

| 资源 \ 稀有度 | 普通 (2 元素) | 稀有 (3 元素) | 史诗 (4 元素) | 传说 (5 元素) |
|--------------|--------------|--------------|--------------|--------------|
| **能量** | `i-relic-energy-1`：闪电+碎裂线 | `i-relic-energy-2`：闪电+多面体轮廓 | `i-relic-energy-3`：环+核心+辐射线 | — |
| **晶体** | `i-relic-crystal-1`：小菱形 | `i-relic-crystal-2`：多菱形组合 | — | — |
| **合金** | `i-relic-alloy-1`：小六边形 | `i-relic-alloy-2`：六边形+条纹 | — | — |
| **数据** | `i-relic-data-1`：小矩形+点 | — | `i-relic-data-3`：轨道+点+核心 | — |
| **暗物质** | `i-relic-dark-1`：小圆+虚线 | `i-relic-dark-2`：圆+内旋线 | `i-relic-dark-3`：漩涡+黑心+环 | — |
| **战斗** | `i-relic-combat-1`：盾+星 | `i-relic-armor`：盾+装甲板线 | `i-relic-combat-2`：圆+波纹 (灵能战徽) | — |
| **探索** | `i-relic-explore`：地图+裂痕 (稀有) | → 同左 | — | — |
| **奇点** | — | `i-relic-capsule`：胶囊+时钟 | `i-relic-singularity`：时钟+裂痕 (奇点印记) | — | — |
| **传说特殊** | — | — | — | `i-relic-silence`：圆+横线+点睛 (静默之眼) |
| **传说终极** | — | — | — | 保留 `i-relic-omega` (欧米伽协议) |

> 矩阵中"—"表示该资源×稀有度组合在当前 20 个遗物中不存在。新增遗物时按其资源类型和稀有度归入对应矩阵格。

### 9.3 矩阵扩展规则

- **新增遗物归位**：新遗物根据其资源类型和稀有度，找到矩阵对应格。
  - 若该格已有图标，直接复用。
  - 若该格为空，设计新图标，元素数量按稀有度标准执行。
- **跨格共享**：允许相邻稀有度共享同一图标，但需在矩阵表中标注（v0.78 起 20 件遗物已无共享实例）。
- **传说级特例**：传说遗物允许脱离资源类型基础形状，使用独立视觉身份（如 `i-relic-silence` 的"静默之眼"），因为传说级本身数量稀少（当前仅 2 个），且需要特殊感。

### 9.4 遗物图标与资源图标的视觉关系

- 遗物图标应保留对原始资源的**视觉呼应**，而非完全照搬资源图标。
- 呼应方式：借用基础形状（如能量遗物用闪电形，晶体遗物用菱形），但增加"碎片感""古老感""封装感"等差异元素。
- **禁止**：遗物图标直接复制资源图标的 SVG path（这正是当前版本的问题，独立化后必须避免）。

## 十、新图标接入流程模板

### 10.1 标准接入流程（6 步）

```
步骤 1：设计 SVG path
    ↓
步骤 2：可读性测试
    ↓
步骤 3：审核
    ↓
步骤 4：添加 symbol 到 Icons.vue
    ↓
步骤 5：更新 data 文件 icon 字段
    ↓
步骤 6：本地验证
```

### 10.2 各步骤详细操作

#### 步骤 1：设计 SVG path

- 依据本规范第一至五章设计 SVG path。
- 在设计工具（Figma / Illustrator / 手写 SVG）中完成 24×24 画布内的路径设计。
- 输出格式：`<path d="..."/>` 字符串。
- **自查清单**：
  - [ ] viewBox 0 0 24 24？
  - [ ] 关键内容在 2-20 范围内？
  - [ ] 元素数量 2-6 个？
  - [ ] stroke-width 1.75（辅助线 1.5）？
  - [ ] stroke-linecap/linejoin round？
  - [ ] fill none（点睛除外）？
  - [ ] 形状语义与图标含义匹配？

#### 步骤 2：可读性测试

- 按第八章方法创建测试页面或在现有测试页中添加新 icon id。
- 在浏览器中检查 24px / 20px / 16px 三尺寸可辨识度。
- **不过审处理**：回到步骤 1 调整路径。

#### 步骤 3：审核

- **设计自查**：完成步骤 1 的自查清单。
- **架构抽查**：架构确认图标语义与实体匹配、命名规范、不与现有图标混淆。
- 审核通过后进入步骤 4。

#### 步骤 4：添加 symbol 到 Icons.vue

在 `src/components/ui/Icons.vue` 的 `<defs>` 内，按注释分区添加新 symbol：

```html
<!-- 遗物图标 -->
<symbol id="i-relic-energy-1" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="1.75" stroke-linecap="round" stroke-linejoin="round">
  <path d="M13 2 4 14h7l-1 8 9-12h-7l1-8z"/>
  <path d="M10 10l4 4" stroke-dasharray="1 2"/>
</symbol>
```

- **注释分区**：按图标类别分组（`<!-- 遗物图标 -->`、`<!-- 科技图标 -->`、`<!-- 建筑图标 -->` 等）。
- **放置位置**：新 symbol 添加在对应注释分区的末尾。
- **symbol id 全局唯一**：添加前全局搜索确认无冲突。

#### 步骤 5：更新 data 文件 icon 字段

在对应的 data 文件中更新实体的 `icon` 字段：

```typescript
// relics.ts 示例
{ id: 'r_energy_1', name: '能量碎片', desc: '...', rarity: 'common', icon: 'i-relic-energy-1', source: '...', effects: [...] }
```

- **icon 字段值必须与 symbol id 完全一致**：注意大小写、连字符。
- **逐文件 diff 核对**：修改后检查是否有遗漏的旧 icon 引用。

#### 步骤 6：本地验证

```bash
cd <项目根目录>

# 1. 类型检查
npx vue-tsc -b

# 2. 构建验证
npm run build

# 3. 单元测试
npx vitest run
```

**验证通过标准**：
- vue-tsc：零错误零警告
- vite build：构建成功
- vitest：全部测试用例通过

**验证失败处理**：
- 类型错误：检查 icon 字段是否与 symbol id 一致。
- 构建失败：检查 SVG 语法是否正确（标签闭合、属性引号）。
- 测试失败：检查测试用例是否硬编码引用了旧 icon id，需同步更新。

### 10.3 接入流程检查清单（一页速查）

```
□ 1. 设计 SVG path（规范 §1-5）
□ 2. 可读性测试 24/20/16px（规范 §8）
□ 3. 审核（设计自查 + 架构抽查）
□ 4. 添加 symbol 到 Icons.vue 对应注释分区
□ 5. 更新 data 文件 icon 字段
□ 6. 本地验证（vue-tsc + build + vitest）
□ 7. 线上验证（部署后目视检查图标渲染）
```
