## 一、两份报告的交集、互补与潜在冲突

### 1.1 交集（双方都指向的同一问题）

| 议题 | 前端报告视角 | 设计报告视角 | 整合结论 |
|------|------------|------------|---------|
| **资源信息冗余** | TopBar 与 Hero 资源重复 | §5.2 视觉噪声：TopBar rate 价值低 + 轨道节点与 TopBar 重复 | 统一由 TopBar 承担资源展示，Hero 聚焦核心能量单一焦点 |
| **事件/推荐重叠** | 合并为单一"行动队列" | §3.3 事件条 vs 行动卡片视觉语言几乎相同 | 合并为单模块（前端主张），内部按"进行中/可执行"两类做视觉区分（设计主张） |
| **Hero 存在感不足** | 尺寸小、无交互 | §4.2 首屏焦点不明确 + §2.4 光晕未渗透 | 尺寸放大 + 光晕渗透 + 核心数值放大 + 交互化，多重手段并用 |
| **字号问题** | 10/11px 偏小 | §2.2 字号层级过细、无模数关系 | 前端的"提升小字号"是治标，设计的"建立模数化 Token"是治本，合并执行 |
| **桌面端空间浪费** | 内容区 max-width 720px 过窄 | §4.1 桌面端单列堆叠浪费横向空间 | 内容区拓宽 + 桌面端双列布局，互补推进 |
| **文明概况扁平** | 缺乏视觉层次 | §3.2 阴影未使用 + §5.1 缺背景层级 | 通过 Elevation 系统 + section 背景区分 + 色条/数值着色组合解决 |

| 维度 | 仅前端覆盖 | 仅设计覆盖 |
|------|-----------|-----------|

| **响应式策略** | SideNav 可折叠 | 四档断点(§4.4) |

### 1.3 潜在冲突（需明确取舍）

**冲突一：资源冗余的处理方向相反**

- 前端 方案 A：Hero 去掉环绕资源，资源交给 TopBar
- 设计 §5.2：TopBar 仅保留 energy，Hero 保留 4 个轨道资源

> **整合决策**：采用**前端方案 A**。理由：TopBar 是全局组件，其他页面（Build/Tech/Explore）也依赖 TopBar 查看资源，若 TopBar 在 HomeView 只剩 energy 会破坏全局一致性。Hero 改为纯氛围 + 能量中心 + 产出率，不再承载资源数值。

**冲突二：事件条与推荐行动是"合并"还是"区分"**

- 前端：合并为单一"行动队列"
- 设计 §3.3：保持两者，通过视觉手段区分

> **整合决策**：采用**前端合并主张 + 设计区分手段**。合并为单一模块，内部分"进行中"（带进度条+脉冲）和"可执行"（带图标色块+hover 上浮）两类视觉语言。既消除信息冗余，又保留两类信息的视觉可辨识度。

**冲突三：字号处理是"微调"还是"重建系统"**

- 前端：10→11、11→12 等逐点提升
- 设计 §2.2：建立 1:1.250 模数化 Token 系统

> **整合决策**：采用**设计主张**，建立模数化字号 Token。前端的逐点提升只是临时补丁，Token 化才能避免未来再次失控。前端 的具体值作为迁移参考。

## 二、统一总目标与设计基调

### 2.1 一句话定调

> **将主界面从"深色主题的 SaaS 工具后台"改造为"沉浸式星际指挥台"——信息去冗余、视觉有层次、交互有反馈、氛围可沉浸。**

### 2.2 四个核心转变（来自设计报告 §7.1，本方案确认采纳）

1. **从 Flat 到 Layered** — 明度差 + inset 高光 + 外阴影三件套建立层次
2. **从 Static 到 Alive** — 星点闪烁、核心脉动、数据 count-up、核心环映射游戏状态
3. **从 Uniform to Hierarchical** — Hero > 行动队列 > 文明概况的明确视觉优先级
4. **从 Tool to Game** — 交互反馈从"功能可用"升级到"操作愉悦"

### 2.3 不可破坏的现有亮点（两份报告共同认可）

- 响应式架构（useBreakpoint + v-if，无 FOUC）
- Design Token 体系雏形（CSS 变量已建立）
- 深空氛围基底（星点 + 核心脉冲 + 环旋转）
- 安全区适配（env(safe-area-inset-bottom)）
- 无障碍基础（prefers-reduced-motion、focus-visible、aria-label）
- 导航数据单一来源（navigation.ts）
- 自托管字体（无 CDN 依赖）

## 三、分阶段推进路线

### P0 · 立即做（1-2 天，高收益/低改动）

> **目标**：消除信息冗余、建立基础规范、提升可读性。改动小、见效快、风险低。

| 序号 | 任务 | 来源 | 责任方 | 前置依赖 | 预期产出 | 验证标准 |

| P0-1 | **Hero 移除环绕资源节点，保留能量中心 + 产出率** | 前端| 前端 | 无 | HomeView Hero 区只显示核心能量值 + 产出率，4 个资源节点删除 | HomeView 同屏内资源不再出现两次 |

**P0 阶段验收标准**：
- HomeView 同屏内无信息重复（资源、转生次数）
- 所有间距、字号、图标尺寸均有 Token 引用（允许少量硬编码待后续迁移）
- 卡片层次肉眼可辨，辅色无偏灰
- 核心数值成为全页视觉焦点

**P0 责任划分**：
- 设计：先出 P0-5、P0-6 的 Token 映射表（一张表说明现状值→Token 名→新值），半天内交付
- 前端：拿到映射表后开始替换，P0-1/2/3/4/7/8 可并行进行

## 五、风险评估

### 5.1 高风险项

| 风险 | 涉及任务 | 影响 | 缓解措施 |
|------|---------|------|---------|
| **CSS 变量全局生效** | P0-3/4、P0-5/6 | style.css 被所有页面共用，改 surface 明度会影响 BuildView/TechView/ExploreView 等 | ① 改动后在所有页面截图对比；② 分批迁移，先 HomeView 验证再全量 |
| **行动队列合并影响跳转逻辑** | P1-2 | activeEvents 和 suggestions 的点击跳转路径需全部保留 | ① 合并前梳理所有跳转路径清单；② 合并后逐条验证；③ 回归测试 Build/Tech/Explore 路由 |
| **桌面端双列布局影响移动端** | P1-3 | 双列布局若用 CSS Grid 实现，需确保 <768px 退化为单列 | ① 使用 `grid-template-columns: 1fr` → `1fr 1fr` 的媒体查询；② 768px 断点上下分别截图 |
| **字体方案引入新字体** | P1-4 方案 A | 引入中文科幻字体增加包体积，可能 FOUT | ① 优先评估方案 B（零新增资源）；② 若选方案 A，字体子集化 + font-display: swap |

### 5.2 中风险项

| 风险 | 涉及任务 | 影响 | 缓解措施 |
|------|---------|------|---------|
| **Token 迁移遗漏** | P0-5/6/8 | 硬编码值散落各组件，可能漏替换 | ① 全局搜索硬编码值（rg "font-size:\s*\d+px"）；② 迁移后用 ESLint/Stylelint 规则禁止硬编码 |
| **核心环信息映射逻辑复杂** | P2-3 | 需读取多个游戏状态计算环的透明度/速度 | ① 先用 mock 数据验证视觉效果；② 再接入真实状态 |
| **交互反馈过度** | P2-4 | 游戏化反馈过多可能显得花哨、影响性能 | ① 遵循 prefers-reduced-motion；② 反馈时长控制在 0.3s 以内；③ 每个反馈只用于一个场景 |
| **SideNav 折叠状态记忆** | P2-8 | localStorage 可能与 SSR 冲突（若有） | ① 确认项目是否 SSR；② 客户端组件内安全读取 localStorage |
