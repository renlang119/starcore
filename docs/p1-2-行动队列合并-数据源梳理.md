## 0. 一句话结论（TL;DR）

- `activeEvents` 与 `suggestions` 在 `HomeView.vue` 内各自为 `computed`，**无独立 store**，均就地组装。
- 两者覆盖的 **路由目标完全相同**：`/build`、`/tech`、`/map`、`/army`，且这 4 条路由在 `router/index.ts` 中全部存在，合并后 **不会丢路由**（最大风险点已验证）。
- 两者信息有 **重合但角色不同**：`activeEvents` 是「单项级、带进度」的细粒度事件条；`suggestions` 是「汇总级、纯引导」的粗粒度卡片。合并为单一「行动队列」时，应按 **状态字段 `status: 'progress' | 'ready'`** 区分两类，而非按来源区分。

## 1. activeEvents 梳理

### 1.1 数据来源

| 字段 | 来源 | 说明 |
|------|------|------|
| `game.buildings` | `useGameStore().buildings`（`stores/buildings.ts`） | `getLevel(id)` / `getCost(id)` |
| `game.research` | `useGameStore().research`（`stores/research.ts`） | `completed` Set / `available(t)` / `count` |
| `game.exploration` | `useGameStore().exploration`（`stores/exploration.ts`） | `progress` 字典 / `getProgress(id, mult)` |
| `game.military` | `useGameStore().military`（`stores/military.ts`） | `trainingQueue` 数组 / `totalUnits` |
| `game.resources` | `useGameStore().resources`（`stores/resources.ts`） | `canAfford(cost)` |
| `game.techCostMult` | `useGameStore().techCostMult`（`computed`，来自 effectSystem） | 科技成本倍率 |
| `game.exploreMult` | `useGameStore().exploreMult`（`computed`，来自 effectSystem） | 探索速度倍率 |
| `BUILDINGS` | `data/buildings.ts` 静态数据 | 建筑定义表 |
| `TECHS` | `data/tech.ts` 静态数据 | 科技定义表 |
| `getNode(id)` | `data/explore.ts` 静态数据 | 探索节点定义 |
| `getUnit(id)` | `data/units.ts` 静态数据 | 兵种定义 |

### 1.2 数据结构

```ts
interface ActiveEvent {
  label: string     // 事件标题，如 "能量收集器 可升级"
  detail: string    // 副标题，如 "Lv.3 → Lv.4" 或 "75%"
  progress: number  // 0~1，1 表示已完成/可执行
  path: string      // 点击跳转路由
  color: string     // 主题色（边框/进度条/图标）
  icon: string      // SVG 图标 id（对应 Icons.vue 中的 <symbol>）
}
```

### 1.3 字段语义详解

- **label**：动态拼接，由「对象名 + 状态动词」构成
- **detail**：
  - 建筑升级：`Lv.{当前} → Lv.{当前+1}`
  - 科技研究：科技效果描述拼接
  - 探索：`{百分比}%` 或 `已完成`
  - 训练：`{百分比}%`
- **progress**：
  - =1 → 资源已够、可立即执行（建筑/科技）
  - <1 → 真实进度百分比（探索/训练）
- **color**：四类事件各有固定主题色
  - 建筑 `#00E5FF`（青）
  - 科技 `#A78BFA`（紫）
  - 探索 `#2EE6A0`（绿）
  - 训练 `#F43F5E`（红）
- **icon**：取自对应数据定义的 `icon` 字段；探索固定用 `i-nav-explore`

### 1.4 生成规则（4 类来源）

| 序号 | 类型 | 触发条件 | progress | path | color |
|------|------|---------|----------|------|-------|
| 1 | 可升级建筑 | `BUILDINGS` 中：未锁定（requires 满足） + 未满级 + `canAfford(getCost)` | `1`（可执行） | `/build` | `#00E5FF` |
| 2 | 可研究科技 | `TECHS` 中：未完成 + `available(t)` + `canAfford(adjustedCost)` | `1`（可执行） | `/tech` | `#A78BFA` |
| 3 | 探索进行中 | `exploration.progress` 中：`startTime≠0` + `!completed` | `getProgress(nodeId, mult)` | `/map` | `#2EE6A0` |
| 4 | 训练进行中 | `military.trainingQueue` 中所有任务 | `1 - remaining/totalTime` | `/army` | `#F43F5E` |

### 1.5 显示截断规则（关键）

```ts
const inProgress = events.filter((e) => e.progress < 1)   // 真实进行中
const ready = events.filter((e) => e.progress >= 1)        // 可执行
return [
  ...inProgress.slice(0, 3),                                // 进行中最多 3 条
  ...ready.slice(0, 4 - Math.min(inProgress.length, 3))    // 可执行补足至总数 4
]
```

- **总条数上限 = 4**
- 进行中优先，最多 3 条
- 剩余位置由可执行项填补
- 合并后若仍要保留「进行中优先」语义，此规则需迁移到新模块

## 2. suggestions 梳理

### 2.1 数据来源

与 `activeEvents` 完全相同的 store 链，但 **不读单项进度**，只读 **数量汇总**。

### 2.2 数据结构

```ts
interface Suggestion {
  label: string  // 汇总标题，如 "3 个建筑可升级"
  desc: string   // 引导文案，如 "资源充足，立即升级"
  path: string   // 点击跳转路由
  color: string  // 主题色
  icon: string   // SVG 图标 id（此处固定用导航图标 i-nav-*）
}
```

### 2.3 字段语义详解

- **label**：以数量打头的汇总句式
- **desc**：纯引导文案，无数据
- **无 progress 字段**：suggestions 不展示进度
- **icon**：全部使用 `i-nav-*` 导航图标（与底部导航一致），而非数据定义中的 icon
- **color**：与 activeEvents 同色系映射

### 2.4 生成规则（4 类来源 + 兜底）

| 序号 | 类型 | 触发条件 | label | path | color |
|------|------|---------|-------|------|-------|
| 1 | 可升级建筑汇总 | 计数 `upgradable > 0` | `{n} 个建筑可升级` | `/build` | `#00E5FF` |
| 2 | 可研究科技汇总 | 计数 `researchable > 0` | `{n} 项科技可研究` | `/tech` | `#A78BFA` |
| 3 | 可探索节点 | `availableExplores.length > 0` | `{n} 个星域待探索` | `/map` | `#2EE6A0` |
| 4a | 训练中汇总 | `trainingQueue.length > 0` | `{n} 支部队训练中` | `/army` | `#F43F5E` |
| 4b | 训练入口（else） | 队列空 + （已有兵种 或 已研究 military_basic） | `训练部队` | `/army` | `#F43F5E` |
| 兜底 | 无任何推荐时 | items 为空 | `建造` + `研究` 两条静态卡片 | `/build`、`/tech` | — |

### 2.5 显示截断规则

- **无截断**：生成多少显示多少
- **兜底机制**：列表为空时强制塞入 2 条静态卡片，避免模块空白

## 3. 两者对比与合并逻辑方案

### 3.1 差异矩阵

| 维度 | activeEvents | suggestions |
|------|--------------|-------------|
| 粒度 | 单项级（每个建筑/科技/节点/任务一条） | 汇总级（按类别聚合数量） |
| 进度 | 有 `progress` 字段（0~1） | 无进度字段 |
| 图标 | 取数据定义 icon（具体对象图标） | 取导航 icon（`i-nav-*`） |
| 截断 | 最多 4 条，进行中优先 | 无截断，空时兜底 2 条 |
| 副标题 | 数据驱动（等级/百分比/效果） | 静态引导文案 |
| 视觉语言 | 条形 + 左边色条 + 底部进度条 | 卡片 + 大图标色块 + hover 上浮 |
| 路由 | `/build` `/tech` `/map` `/army` | `/build` `/tech` `/map` `/army` |

### 3.2 重叠与冗余分析

- **完全重叠**：建筑、科技、探索、训练四类信息在两个模块中各出现一次
- **差异信息**：
  - activeEvents 独有：单项级别进度、具体等级/百分比
  - suggestions 独有：数量汇总、训练入口（无训练时引导）、空状态兜底
- **合并价值**：消除 4 类信息的重复展示，但需保留两者各自的独特价值

### 3.3 合并方案：按 `status` 分类，不按来源分类

> 设计稿要点：合并为单一「行动队列」模块，内部分 **进行中** 与 **可执行** 两类视觉语言。

#### 3.3.1 分类标准

| 分类 | 判定条件 | 视觉语言（参考总体方案 P1-2） |
|------|---------|----------------------------|
| **进行中 `progress`** | 真实进度 0 ≤ progress < 1（探索/训练中） | 进度条 + 脉冲 box-shadow |
| **可执行 `ready`** | progress = 1（资源已够可立即操作）或纯引导入口 | 图标色块 + hover 上浮 |

#### 3.3.2 合并后数据结构建议

```ts
interface ActionItem {
  id: string              // 唯一 key，用于 v-for（合并后必须显式生成，不能用数组下标）
  category: 'build' | 'tech' | 'explore' | 'army'  // 业务分类，对应 4 条路由
  status: 'progress' | 'ready'   // 进行中 / 可执行
  label: string           // 主标题
  detail: string          // 副标题（进度/等级/数量等）
  progress?: number       // 仅 status='progress' 时存在，0~1
  path: string            // 跳转路由
  color: string           // 主题色
  icon: string            // 图标 id
  count?: number          // 可选：同类数量（保留 suggestions 的汇总语义）
}
```

#### 3.3.3 合并策略（去重 + 互补）

| 业务分类 | 进行中（progress）来源 | 可执行（ready）来源 | 合并后展示规则建议 |
|---------|----------------------|-------------------|------------------|
| 建筑 | — | activeEvents 的「可升级建筑」单项 | 若有 ≥1 个可升级建筑，展示 1 条汇总卡片（count=n），点击跳 `/build`；不再逐条列 |
| 科技 | — | activeEvents 的「可研究科技」单项 | 同上，展示 1 条汇总卡片 |
| 探索 | activeEvents 的「探索进行中」单项 | suggestions 的「可探索节点」汇总 | 进行中逐条展示（保留进度）；可执行展示 1 条汇总卡片 |
| 训练 | activeEvents 的「训练进行中」单项 | suggestions 的「训练部队」入口 | 进行中逐条展示；可执行展示 1 条入口卡片 |
| 兜底 | — | 无任何推荐时 | 保留 suggestions 的 2 条静态卡片兜底 |

**关键决策**：
- **建筑/科技**：合并后用「汇总卡片」代替「逐条列出」，避免队列过长（原 activeEvents 上限 4 条已暴露此问题）
- **探索/训练**：进行中保留逐条展示（用户需要看具体进度），可执行用汇总卡片
- **截断规则**：进行中上限 3 条（沿用原规则），可执行无上限但不强制展示全部（建议最多 4 条）

## 5. 合并后数据结构最终建议

> **最终落地口径（v0.49 回写）**：实现与本节建议有三处有意偏离，统一口径如下——
> 1. `ActionItem` **不带** `category`/`count` 字段：汇总文案直接写入 label（如「3 个建筑可升级」），字段无消费方
> 2. 截断规则为「**进行中全保留**（天然上限 7 = 4 探索 + 3 训练槽）**+ 可执行补足至总数 ≤6**」，而非「进行中 ≤3」——进行中条目承载实时进度，截断会丢信息
> 3. SG-4a 训练汇总卡**已按本节建议移除**（v0.49 起），训练进度由进行中条目承担
>
> 以下为原始设计建议，保留作历史脉络。

### 5.1 完整 ActionItem 定义

```ts
interface ActionItem {
  id: string
  category: 'build' | 'tech' | 'explore' | 'army'
  status: 'progress' | 'ready'
  label: string
  detail: string
  progress?: number        // status='progress' 时必填
  path: string
  color: string
  icon: string
  count?: number           // 汇总卡片时填，表示同类数量
}
```

### 5.2 生成逻辑伪代码

```ts
const actionQueue = computed<ActionItem[]>(() => {
  const items: ActionItem[] = []

  // —— 进行中（progress）——
  // 1. 探索进行中（逐条）
  for (const [nodeId, prog] of Object.entries(game.exploration.progress)) {
    if (prog.startTime === 0 || prog.completed) continue
    const node = getNode(nodeId)
    if (!node) continue
    const progress = game.exploration.getProgress(nodeId, game.exploreMult)
    items.push({
      id: `explore-${nodeId}`,
      category: 'explore',
      status: 'progress',
      label: `探索 ${node.name}`,
      detail: progress >= 1 ? '已完成' : `${Math.floor(progress * 100)}%`,
      progress,
      path: '/map',
      color: '#2EE6A0',
      icon: 'i-nav-explore',
    })
  }

  // 2. 训练进行中（逐条）
  for (const task of game.military.trainingQueue) {
    const unitDef = getUnit(task.unitId)
    if (!unitDef) continue
    const progress = 1 - task.remaining / task.totalTime
    items.push({
      id: `train-${task.id}`,
      category: 'army',
      status: 'progress',
      label: `训练 ${unitDef.name} ×${task.count}`,
      detail: `${Math.floor(progress * 100)}%`,
      progress,
      path: '/army',
      color: '#F43F5E',
      icon: unitDef.icon,
    })
  }

  // —— 可执行（ready）——
  // 3. 建筑可升级（汇总）
  const upgradable = countUpgradableBuildings()
  if (upgradable > 0) {
    items.push({
      id: 'ready-build',
      category: 'build', status: 'ready',
      label: `${upgradable} 个建筑可升级`,
      detail: '资源充足，立即升级',
      path: '/build', color: '#00E5FF', icon: 'i-nav-build',
      count: upgradable,
    })
  }

  // 4. 科技可研究（汇总）
  const researchable = countResearchableTechs()
  if (researchable > 0) {
    items.push({
      id: 'ready-tech',
      category: 'tech', status: 'ready',
      label: `${researchable} 项科技可研究`,
      detail: '解锁新技术',
      path: '/tech', color: '#A78BFA', icon: 'i-nav-tech',
      count: researchable,
    })
  }

  // 5. 可探索节点（汇总）
  const availableExplores = game.exploration.availableNodes()
  if (availableExplores.length > 0) {
    items.push({
      id: 'ready-explore',
      category: 'explore', status: 'ready',
      label: `${availableExplores.length} 个星域待探索`,
      detail: '开拓新星域',
      path: '/map', color: '#2EE6A0', icon: 'i-nav-explore',
      count: availableExplores.length,
    })
  }

  // 6. 训练入口
  if (game.military.trainingQueue.length === 0 &&
      (totalUnits.value > 0 || completedTechs.has('military_basic'))) {
    items.push({
      id: 'ready-army',
      category: 'army', status: 'ready',
      label: '训练部队',
      detail: '增强军事实力',
      path: '/army', color: '#F43F5E', icon: 'i-nav-army',
    })
  }

  // —— 兜底 ——
  if (items.length === 0) {
    items.push(
      { id: 'fallback-build', category: 'build', status: 'ready',
        label: '建造', detail: '升级建筑提升产能',
        path: '/build', color: '#00E5FF', icon: 'i-nav-build' },
      { id: 'fallback-tech', category: 'tech', status: 'ready',
        label: '研究', detail: '解锁新技术',
        path: '/tech', color: '#A78BFA', icon: 'i-nav-tech' },
    )
  }

  // —— 截断：进行中优先，最多 3 条；可执行补足至总数 ≤ 6 ——
  const progress = items.filter(i => i.status === 'progress').slice(0, 3)
  const ready = items.filter(i => i.status === 'ready').slice(0, 6 - progress.length)
  return [...progress, ...ready]
})
```

### 5.3 与原模块的语义对照

| 原始信息 | 原所在模块 | 合并后去向 | 保留情况 |
|---------|----------|----------|---------|
| 建筑单项可升级（label/detail/level） | activeEvents | 合并为汇总卡片 `ready-build`（count=n） | ✅ 信息聚合，不丢路由 |
| 科技单项可研究（label/effects） | activeEvents | 合并为汇总卡片 `ready-tech`（count=n） | ✅ 信息聚合，不丢路由 |
| 探索单项进行中（label/progress%） | activeEvents | 逐条保留为 `progress` 项 | ✅ 原样保留 |
| 训练单项进行中（label/progress%） | activeEvents | 逐条保留为 `progress` 项 | ✅ 原样保留 |
| 建筑汇总（n 个可升级） | suggestions | 合并到 `ready-build` | ✅ 去重合并 |
| 科技汇总（n 项可研究） | suggestions | 合并到 `ready-tech` | ✅ 去重合并 |
| 探索汇总（n 个待探索） | suggestions | 保留为 `ready-explore` | ✅ 保留 |
| 训练汇总（n 支训练中） | suggestions SG-4a | 不再单独展示（与 progress 项信息重复） | ⚠️ 见下方说明 |
| 训练入口（无训练时引导） | suggestions SG-4b | 保留为 `ready-army` | ✅ 保留 |
| 空状态兜底 | suggestions SG-F1/F2 | 保留 | ✅ 保留 |

> ⚠️ **SG-4a 的处理说明**：原 suggestions 在有训练队列时展示「N 支部队训练中」，这与 activeEvents 的训练逐条展示信息重复。合并后建议 **不再单独展示此汇总卡片**，训练信息统一由 `progress` 项承担。若设计稿希望保留汇总入口，可在 progress 项上方加一条「训练汇总」作为 section header，但不再作为独立可点击卡片。

## 6. 风险与建议

### 6.1 已识别风险

| 风险 | 等级 | 说明 | 缓解措施 |
|------|-----|------|---------|
| 跳转路由丢失 | 高（P1-2 最大风险点） | 合并后某些原始跳转入口可能被遗漏 | 本文档 §4 已逐条验证，4 条路由全部保留，7 条入口均有对应展示位 |
| 建筑可升级数量过多导致卡片膨胀 | 中 | 合并后建筑/科技用汇总卡片，若 count 很大视觉突兀 | 建议设计稿对 count > 9 时显示「9+」 |
| 进行中项被汇总卡片挤压 | 中 | 若 ready 项很多，progress 项可能被截断 | 沿用原规则：progress 优先，最多 3 条；ready 补足 |
| 兜底状态与空状态混淆 | 低 | 合并后兜底 2 条卡片与正常 ready 卡片视觉无区分 | 建议设计稿为兜底态加「开始你的旅程」类文案区分 |
| id 字段缺失导致 v-for key 警告 | 低 | 原 activeEvents 用数组下标 `i` 作 key | 合并后 ActionItem 显式生成 id，避免用下标 |

### 6.2 给设计的建议

1. **两类视觉语言需明确区分**：
   - `progress` 类：进度条是核心视觉元素，建议保留原 activeEvents 的左边色条 + 底部进度条
   - `ready` 类：图标色块是核心视觉元素，建议保留原 suggestions 的大图标 + hover 上浮
2. **汇总卡片的 count 展示**：建议在图标右上角加角标，或在 label 中突出数字
3. **进行中与可执行的排序**：建议进行中在上、可执行在下，中间可有微妙分隔（不强分隔）
4. **空状态兜底**：建议设计专门的「开始你的旅程」空状态视觉，而非复用 ready 卡片

### 6.3 给前端落地的建议

1. **不新增 store**：合并后的 `actionQueue` 仍为 HomeView 内的 `computed`，与原架构一致
2. **复用现有数据源**：所有数据来源不变，仅重组装逻辑
3. **回归测试重点**：
   - 4 条路由跳转逐条点击验证
   - 空状态兜底正常显示
   - 探索/训练进度实时更新
   - 建筑可升级时汇总卡片 count 正确
4. **保留原 activeEvents/suggestions 的计算逻辑作为参考**：合并 PR 中建议保留注释或 git history 可追溯
